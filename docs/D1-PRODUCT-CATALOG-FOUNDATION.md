# D1 product catalog foundation (Task 2A)

Migration `057_marketplace_product_catalog.sql` creates `marketplace_products`. It stores stable product identity (`id`, immutable `slug`), Creator ownership (`creator_id` and optional one-to-one `creator_listing_id`), publication and storefront status, buy mode, core descriptive fields, currency, fixed/free/PWYW pricing, sale schedule, explicit cover/preview/thumbnail/delivery R2 keys, delivery filename and content type, and JSON metadata for the remaining catalog details (authors, formats, tags, features, version, discovery attributes, and similar fields). `created_at`, `updated_at`, `published_at`, and `revision` support history and controlled updates.

The migration does **not** alter `order_items`, `download_entitlements`, or `creator_sale_snapshots`. Those records retain their sale-time product slug, title, price, identity, and delivery-key snapshots. Product slugs, IDs, and Creator ownership cannot be changed. Published products and products with purchase history are retired instead of deleted; unsold drafts may be removed. Existing Creator listing IDs can be used as product IDs during migration, with `creator_listing_id` preserving the explicit relationship. A linked listing must belong to the same Creator.

`functions/_lib/product-catalog-d1.mjs` provides `createProduct`, `getProductById`, `getProductBySlug`, `listProducts`, and `updateProduct`. It uses only Cloudflare D1 prepared statements. Create and update validate pricing and R2 keys; updates use `revision` to reject stale writes. `listProducts` supports Creator, publication-state, and storefront-status filters with bounded pagination. Flexible `metadata` may not shadow authoritative columns.

Migration 057 is applied to `trg-orders-staging` only. Task 2C added `/owner/api/catalog-publication`, which uses the existing Owner account session and CSRF checks, native staging D1/R2 bindings, unique create-only R2 keys, upload verification, and a final published D1 insert. The old Owner Intake publication route still returns 503. Staging verification published and removed a disposable product, checked both R2 objects and D1 lookups, and confirmed cleanup after a controlled D1 failure. Production D1 and R2 remain untouched.

`/api/catalog` now provides read-only D1 lookup and listing of published products. Its public projection excludes private R2 delivery keys and unapproved metadata fields. Storefront pages, checkout, fulfillment, and Owner Intake do not yet consume this API.

Task 2D changed `/product-assets/{slug}/{asset}` to resolve published products and approved `cover.webp` or `preview.webp` keys from D1, then read the object through the private `TRG_PRODUCTS` binding. The route rejects unpublished products, missing objects, non-WebP objects, delivery keys, and every other asset name. Native staging verification retrieved a disposable cover through the preserved public URL and confirmed that PDF paths remained inaccessible.

## Remaining integration requirements

The repository's current `data/products.json`, generated runtime catalog, and product folder map are empty, so there are no existing product rows to backfill from them at this checkpoint. Remaining work must connect storefront pages, Owner reads and Intake, checkout, downloads, pricing, homepage, bundle, Creator, and inactivity consumers to D1 while preserving historical snapshots. Keep the old publication actions unavailable until their Cloudflare reads and writes are connected and verified.
